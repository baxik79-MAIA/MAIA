# ADR-0032: Versioned Action Binding and Execution Authorization

**Status:** Accepted
**Date:** 2026-09-11
**Decision owner:** MAIA architecture
**Milestone:** M0.1.1
**Product version:** 1.3.0

## Context

M0.1 introduced structural execution-domain types but deliberately deferred
authorization. The architecture owner resolved the missing action revisions,
binding canonicalization, approval/CAS versions, policy/assurance semantics,
execution evidence, retry identity and pause scope in the M0.1.1 directive.
Required fields and Run FSM edges change; this is contract evolution from 1.2.1,
not a backward-compatible patch.

## Decision

`spec/domain.yaml`, `spec/action_binding.yaml`, `spec/approval.yaml`,
`spec/execution.yaml`, `spec/states.yaml` and `spec/sync.yaml` are authoritative.

An ActionId is a logical step. ActionId/version and PlanId/version identify
reconstructible execution snapshots. Binding fields become immutable after
approval binding or any Run. Material edits increment the Action version once;
identity changes create a new ActionId. Every executable revision has an Approval
binding record, including truthful autonomous `not_required` records.

ActionBindingV1 explicitly uses RFC8785 JCS, UTF-8 and SHA-256, separately from MCP
definition fingerprints. Its exact projection includes canonical input and
canonicalizer identity, connector selection/profile/binding, visible MCP fingerprint,
final risk, and source preconditions. Versions in the hashed projection are decimal
strings preserving all u64 values. Source tuples sort by raw UTF-8 bytes and exact
duplicates fail closed. State, results, UI and transient Run data are excluded.
Canonical input must reproduce all material effect semantics; mutable locators
cannot replace content-addressed bytes. Missing material canonicalizers fail closed.

ConnectorSelection distinguishes connectorless `none`, identity-bound `fixed`, and
non-material `policy_routed`. Material connector effects require fixed selection.
ConnectorBindingV1 covers non-secret account/tenant/resource execution identity;
same profile ID cannot mask changed execution authority. Current connector, input,
and MCP tool fingerprints are rechecked. Production resolvers remain deferred.

Approval.version is record CAS version, never Action.version. A new binding gets
a new ApprovalId/version 1. Immutable binding fields and record versions remain
auditable. Human decisions atomically match record identity/version/state and the
current executable Action revision/hash, plus expiry and authorized actor checks.
System expiry/revocation are lifecycle operations, not human approve/reject commands.
Actual atomicity belongs to the future authoritative store. Version/attempt overflow
always fails closed without wrap, saturation or identity reuse.

PolicyDecision has the explicit restriction order allow, confirm,
elevated_confirm, deny. All applicable layers compose toward greater restriction.
Scoped grants only allow autonomous policy-gated work with explicit scope permission;
they cannot make canonical confirm/elevated_confirm gates autonomous. A deny is
audited as policy evaluation, not fabricated as human approval. Plan GateType remains
an informational gate summary; deny is a separate policy outcome.

ApprovalAssurance records none/confirm/elevated_confirm, independently of technology.
Binding validity is distinct from execution authorization and history. Current
policy and achieved assurance govern the authorization matrix; expiry uses
now >= expires_at. Expired approved records stay approved but cannot execute.
Material divergence retains ADR-0031's exception: revoke pending/approved and preserve
the other historical states. Earlier approval cannot defeat a later deny or stronger
assurance requirement. Policy snapshot identity records the original evaluation;
policy administration and materialization are deferred.

A Run binds ActionId/version/hash and ApprovalId/record-version. Its result affects
only that Action revision. Attempts count within ActionId/version; retry creates a
new RunId, whereas a new Action revision resets attempt to 1. Run.retryable_error
has no outgoing edges and remains the historical result of that attempt.

Reconciliation requires authoritative effect_confirmed/effect_not_executed evidence;
search absence alone is insufficient. Unresolved effects block semantically equivalent
re-execution even across different IDs/revisions. Freshness evidence binds the same
exact Run/action revision/hash, includes source observations and enforcement mode,
and cannot authorize another Run. Unverifiable material freshness fails closed.
Compare-before-execute does not claim atomic source protection or remove TOCTOU.

Task pause counts all in-flight Runs, including superseded revisions. Starting,
running, outcome_unknown and reconciling are in-flight. After pause request no new
Run is created/scheduled and no created Run starts. Action has no paused state.

Trusted effective-recipient context resolves internal/external/unknown. Unknown is
external risk, empty mail recipients fail closed, and only a private no-attendee
calendar event gets the internal-write rule. Explicit destructive/privileged
operation floors survive recipient classification without inventing a global risk
ordering. Production directory expansion is deferred.

## Consequences and scope

M0.1.1 changes contracts, Spec Guard, reference/golden/negative tests, generated
documentation and mechanical Rust domain conformance. Reference oracles in tests
are not the M0.2 policy engine or atomic persistence. Domain constructors validate
structure; they do not prove trusted observations, current authorization or effect
equivalence. No connectors, scheduler, network services, UI or dashboard are added.

Historical ADRs retain their text; direct amendments point here. Existing master
documentation remains historical and below canonical spec authority. Database
migrations are not implemented because there is no authoritative runtime store yet.
Consumers of 1.2.1 contracts must explicitly adapt to 1.3.0.

## Alternatives rejected

- Conflating Action revision and Approval CAS version.
- Using native JSON numbers for full u64 hash inputs.
- Reusing a Run or proof after retry or hiding old in-flight work by supersession.
- Treating valid binding, familiarity or historic approval as current authority.

These alternatives lose identity, evidence or authorization guarantees.

## Conformance clarification — M0.1.2 / MAIA 1.3.1

Architecture Desk accepted post-commit findings F1–F4. Canonical Run terminal states
have no outgoing edges, enforced by the validator. Stored Approval policy snapshots
must agree with lifecycle state and assurance. Rejection is an attributable human
decision requiring actor/time/surface and confirm assurance, even when approval
requires elevated_confirm. Pending has no human-decision metadata. Input completeness
is validated before risk floors. See current canonical YAML and the M0.1.2 development
note. This corrective patch preserves M0.1.1 history and does not add runtime or UI.
