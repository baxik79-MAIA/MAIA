# ADR-0047: Claude Code subscription provider as a Round Table participant adapter

Status: Accepted (M0.12 vertical slice)

Canonical contract: `spec/claude_code_provider.yaml`
Related: ADR-0046 (Round Table is an optional external module),
`spec/round_table.yaml`, `directives/MAIA_Architecture_Amendment_Autonomous_Evolution_Deployment_Lock_v5.1.md`

## Context

Round Table already defines a provider-neutral `Participant` port
(`roundtable`, formerly `core/roundtable`; relocated at M0.15.8) and one
concrete adapter, `infra/anthropic`, which calls
the Anthropic Messages API using `ANTHROPIC_API_KEY`.

MAIA's development host has an authenticated Claude Code CLI backed by a
`stripe_subscription` OAuth session. Using it as a Round Table participant
removes both the metered API-key dependency and the manual copy/paste loop
between MAIA and Claude. The requirement is a *programmatic* participant, not
a second reasoning brain and not an execution path.

## Decision

Add `infra/claude-code` (`maia-claude-code`): an infra adapter that implements
the existing `maia_roundtable::Participant` port by invoking the locally
authenticated Claude Code executable as a child process.

`core/*` is unchanged. The dependency direction stays
`adapter -> core contracts`, never the reverse, per ADR-0046.

## Decisions that deviate from the naive invocation pattern

### 1. No `--permission-mode bypassPermissions`

A Round Table participant is reasoning-only: `spec/round_table.yaml` sets
`execution_authority: forbidden`, and AGENTS.md states that reasoning
assurance never grants execution permission. `bypassPermissions` would give a
consultation participant unattended write and shell authority over the
development host — strictly more authority than the port it implements is
allowed to have.

The provider therefore never passes `bypassPermissions`.

### 2. Deny-list, not an empty allowlist

Measured on Claude Code 2.1.273 during this slice:

- `--allowed-tools ""` did **not** restrict anything. The child still read a
  repository file, `num_turns: 2`, `permission_denials: []`. An empty
  allowlist is a no-op, not deny-all.
- `--disallowed-tools Read Glob Grep Bash Edit Write WebFetch WebSearch Task
  NotebookEdit` **did** hold: the same prompt returned `CANNOT_READ`.

Tool authority is therefore restricted by an explicit deny list. Egress tools
(`WebFetch`, `WebSearch`) are always denied so a consultation cannot become an
uncontrolled egress path, which preserves the privacy/egress invariant.

### 3. Unconditional `ANTHROPIC_API_KEY` scrub

`ANTHROPIC_API_KEY` is present in the development host environment. A child
process inheriting it would silently leave subscription-backed authentication
and bill as metered API usage under a different credential boundary — exactly
the "no hidden model or connector fallback" invariant this provider must
preserve.

The provider unconditionally removes `ANTHROPIC_API_KEY`,
`ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS`,
`ANTHROPIC_MODEL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and
`AWS_BEARER_TOKEN_BEDROCK` from the child environment. This is a scrub, never
an injection: the provider introduces no API key and reads none.

### 4. Prompt delivered on child stdin

The packet is serialized to JSON and written to the child's stdin rather than
placed in `argv`. Process invocation is argument-safe (`std::process::Command`,
no shell); stdin additionally avoids the Windows command-line length ceiling
for realistic review packets containing diffs.

### 5. Cost is recorded as unknown

The CLI reports `total_cost_usd` on a `costBasis: "list"` basis. Under a
subscription that number is not actual spend. Per the "unknown cost is never
treated as zero" invariant, the adapter records token counts and sets
`cost_known: false` rather than inventing a monetary amount.

## Versioned contracts

`maia.consultation_packet.v1` and `maia.consultation_result.v1` are carried in
the adapter, not in Core. The result is schema-validated — including that
`consultation_id` matches the request — *before* Round Table consumes it. A
malformed, empty, mismatched or schema-violating response is a permanent
failure. The adapter never synthesizes a response, never falls back to another
provider, and never reports success it did not receive.

## Recursion prevention

The child is given `MAIA_CLAUDE_CODE_PROVIDER_ACTIVE=1`. If that marker is
already present when the provider is constructed, invocation is refused as a
permanent failure. This prevents a Claude Code consultation from recursively
spawning further Claude Code consultations.

## DEPLOYMENT_LOCKED absence by construction

v5.1 §6.2 requires that self-improvement capability be absent by construction
rather than disabled by a runtime boolean. Accordingly:

- all subprocess code lives behind the non-default cargo feature
  `development-evolution` and is not compiled without it;
- without the feature, `capability_present()` is `false` and construction
  returns `CapabilityAbsent`;
- no MAIA Core crate and no shipped application depends on `maia-claude-code`,
  so a DEPLOYMENT_LOCKED build omits it from the build graph entirely.

The running instance cannot re-enable the capability; doing so requires an
external rebuild with the feature enabled.

## Consequences

- MAIA/Round Table can consult Claude Code programmatically with no API key
  and no manual relay.
- The adapter is one more provider behind an existing neutral port; Round
  Table remains provider-neutral and optional.
- The provider is host-dependent: it requires an installed, authenticated
  Claude Code CLI, and fails closed when that is missing.
- Live invocation is opt-in (`MAIA_LIVE_CLAUDE_CODE=1`) and read-only;
  deterministic tests use an injected fake process runner.
