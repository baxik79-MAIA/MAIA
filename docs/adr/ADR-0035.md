# ADR-0035: transactional runtime coordinator

Status: Accepted by Architecture Desk for M0.4 implementation
Date: 2026-09-12

## Decision

M0.4 adds one application layer, `core/runtime`, above the existing pure
`maia-domain`, `maia-policy`, `maia-orchestrator` and `maia-store` crates.
Runtime commands receive already-resolved input, policy, actor, freshness and
routing facts. They compose the existing policy/orchestrator functions and
invoke exactly one authoritative store operation for each canonical T1–T5
boundary.

The layer exposes separate action, approval, run and pause modules. It returns
typed local outcomes for created, blocked, needs-evidence and conflict paths.
It never resolves providers, reads SQLite directly, performs filesystem or
connector I/O, starts schedulers, or executes side effects.

`prepare_run` constructs an in-memory `Run(created)` only after the current
authorization, exact binding, routing, freshness and tool checks are composed;
the atomic T3 store command is called only when all gates allow it. Run
transitions apply pure freshness/reconciliation decisions and the domain FSM
before atomic T4. Pause only requests canonical `Running -> Pausing`; supplied
in-flight Run facts determine whether quiescence has been reached, while store
T3/T4 race guards remain authoritative.

## Consequences

`infra/sqlite` remains a composition adapter and is used by integration tests
only. Runtime does not duplicate business rules from policy or orchestrator,
and no new canonical YAML field, wire enum or state transition is introduced.
