# ADR-0036: one-shot executor boundary and run driver

Status: Accepted by Architecture Desk for M0.5

## Decision

Add one pure `core/executor` crate above `maia-domain`, `maia-policy`,
`maia-orchestrator`, `maia-runtime` and `core/store`. It exposes a small
`ActionExecutor` port and an explicit `execute_run` driver. The driver loads
the authoritative Run, action revision and Approval, revalidates their exact
binding plus current policy, freshness, routing and actor facts, then uses the
existing atomic T4 port to claim `created -> starting` and enter `running`.

The injected executor receives only an `ExecutionRequest` containing the exact
Run/action/Approval material. Its semantic result maps to the existing Run
states: success to `completed`, final failure to `failed`, retryable failure to
`retryable_error`, and uncertainty to `outcome_unknown`. The driver persists
the result before reporting it. A panic or process interruption leaves the
in-flight Run for reconciliation; `recover_incomplete_runs` only reports
candidates and never retries or performs a side effect.

## Boundaries

`core/executor` has no connector, filesystem, SQLite, network, scheduler,
worker or UI dependency. It does not add a canonical wire enum or change the
canonical YAML. Concrete connectors and a future scheduler are composition
responsibilities outside this milestone.

The T4 store command remains the authority for CAS, pause races, evidence,
audit and atomic persistence. The executor port cannot access a store or
workspace, and a second `execute_run` call cannot invoke the port after the
first successful claim.
