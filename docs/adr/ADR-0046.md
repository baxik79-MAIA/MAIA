# ADR-0046: Round Table leaves MAIA Core as an optional external module

Status: Accepted — Architecture Owner decision

## Context

Round Table has been documented as a reusable multi-model consultation
subsystem since `09_ROUND_TABLE.md` and the Product Vision Round Table
objective, but its position relative to MAIA Core remained ambiguous:
earlier text left open whether Round Table's implementation would ship
inside the MAIA Core runtime/build or beside it. This ADR is the
free-standing canonical source for that resolution and its consequences
for the repository; it does not derive its authority from Architecture
Directive v5.1
(`directives/MAIA_Architecture_Amendment_Autonomous_Evolution_Deployment_Lock_v5.1.md`),
a separate, compatible directive that governs `DEVELOPMENT_EVOLUTION` /
`DEPLOYMENT_LOCKED` and the Evolution Supervisor. Round Table must still
obey every applicable Policy/Approval/`execution_authority`/egress/
deployment-lock constraint v5.1 and other canonical contracts impose, but
neither document supersedes or is sourced from the other.

## Decision

Round Table SHALL NOT remain part of MAIA Core. It becomes an **optional
external module**. The working product name may remain "MAIA Round Table"
until separately renamed.

## Dependency direction

```
MAIA Round Table
        |
        v
public MAIA contracts / Intelligence Fabric interfaces
```

Never the reverse. MAIA Core MUST NOT require the Round Table
implementation to start, operate, brief, reason, manage memory, use local
intelligence, use normal provider routing, or perform its standard
workflows. MAIA must be a complete product with Round Table entirely
absent.

## Core invariants introduced

- Round Table failure is non-fatal: unavailable, disabled, uninstalled,
  misconfigured or offline leaves MAIA Core operating normally, with no
  hidden fallback, no boot dependency and no required DB migration solely
  because Round Table is absent.
- Round Table cannot bypass Privacy, Policy, Approval, `execution_authority`,
  egress rules, credential boundaries or audit requirements. External
  models participating in Round Table receive only the minimum context
  MAIA's policy/egress layer permits. Round Table is never an alternate
  execution path around MAIA governance.
- Round Table is not MAIA's memory owner, policy owner, Approval authority,
  execution authority, persistent state owner, provider router, or core
  orchestration engine. It is an optional reasoning capability only:
  multi-model debate, independent perspectives, structured adversarial
  review, specialist roles, synthesis, brainstorming, and decision support.
- The provider-neutral MAIA Intelligence Fabric is NOT extracted merely
  because Round Table is leaving Core. MAIA still owns normal
  intelligence/model routing; Round Table consumes approved intelligence
  interfaces/contracts rather than owning MAIA's fundamental model
  architecture.
- After extraction, an explicit test MUST prove MAIA builds and operates
  with Round Table absent/disabled. Round Table may depend on MAIA public
  contracts; MAIA Core must not depend on the Round Table implementation.

## Migration strategy

Physical separation is deferred until the current M0.11 Windows
qualification reaches a stable boundary (do not interrupt active
qualification work to restructure crates). At the first safe boundary,
proceed in three phases:

1. **Analyze** — inspect all current dependencies on the Round Table port crate
   (direct crate/type/persistence dependencies, tests, docs, runtime call
   sites, Intelligence Fabric coupling, accidental Core assumptions) and
   produce an exact dependency map.
2. **Define contract** — the smallest provider-neutral boundary an
   external Round Table module needs, preferring existing interfaces over
   inventing a large plugin framework: MAIA request -> bounded context
   package -> external Round Table reasoning -> structured result -> MAIA
   verification/synthesis/use. Round Table receives no implicit authority.
3. **Extract** — move the Round Table implementation (participant-role
   logic, debate orchestration, multi-model deliberation, debate
   transcripts/state, Round-Table-specific synthesis) outside MAIA Core
   into an optional module, following existing workspace conventions.
   Repository (multi-repo) separation is a later, separate evaluation;
   logical/module separation comes first.

No additional user approval is required for the separation itself; this
is an accepted decision, not an RFC.

## Extraction status (M0.15.8)

The M0.11 Windows qualification boundary named above was reached (M0.15.7f
closed the protected-work reconciliation that had been holding it open).
Phases 1 and 2 (Analyze, Define contract) were already satisfied before this
milestone: the dependency-direction invariant in this ADR was already fully
enforced by the Cargo dependency graph and proven by
`roundtable/tests/core_independence.rs` (D009) — see Architecture Desk ruling
2026-09-17, recorded in that test's own module documentation, that the
dependency graph is what proves this boundary, not workspace layout.
Phase 3 (Extract) — the physical move — completed at M0.15.8: the crate
formerly at `core/roundtable` now lives at `roundtable/` (top-level, sibling
to `core/`, `infra/`, `composition/`, `apps/`, `ops/`), package name
`maia-roundtable` unchanged. No dependency edge changed; only path strings did.
Repository (multi-repo) separation remains a later, separate evaluation, not
addressed here.

## Consequences

- `roundtable/` (the crate `maia-roundtable`, formerly `core/roundtable`) is
  treated as an optional dependency of the workspace, consumed by no required
  Core path.
- Commercial/packaging treatment of the module (bundled optional,
  separately installed, advanced/professional capability, internal
  development tool, or separate product) is deliberately left open and is
  not decided by this ADR.
- `09_ROUND_TABLE.md` and `14_PRODUCT_VISION_AND_USER_PROFILES.md` are
  updated with concise references to this decision rather than duplicating
  it.
- Development-host autonomous evolution (the `DEVELOPMENT_EVOLUTION`
  capability profile defined in v5.1) may perform this extraction without
  per-mutation Architecture Desk approval once the current M0.11
  qualification reaches a stable boundary, subject to v5.1's own
  protected-surface and Evolution Supervisor boundaries.

## Compatibility

Additive/forward-compatible. No existing accepted M0.0-M0.10 contract is
reopened by this decision. `DEPLOYMENT_LOCKED` semantics (defined in v5.1)
are unaffected and are not weakened by Round Table's optionality.
