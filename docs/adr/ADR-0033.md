# ADR-0033: Authoritative Persistence, Audit and Transaction Boundaries

## Status

Accepted for M0.2.1 contract closure. Store implementation is deferred to a
later milestone.

## Context

MAIA execution history must survive restart without allowing a persistence
adapter to invent ownership, concurrency or audit semantics. The local profile
will eventually use SQLite, while enterprise deployments may use another
transactional store. Both need one mutable authority per workspace and the same
observable contract.

## Decision

The canonical contracts in `spec/persistence.yaml`, `spec/audit.yaml` and the
typed execution contracts in `spec/domain.yaml` define the boundary.

- `Workspace` owns the mutable task and workspace audit authority.
- Plan and Action versions are immutable revisions. Approval binds an exact
  Action revision and hash. Run binds that same revision plus an exact Approval
  record and version. Supersession preserves history; runtime hard-delete APIs
  are forbidden.
- `AgentTask.version` and `Run.version` are mutable record CAS counters,
  distinct from Action/Plan revision numbers and Run attempt numbers. A
  successful mutation matches expected version and state, then increments with
  checked overflow.
- Authority-changing writes are serialized. T1 creates a material Action
  revision and handles old/new approvals and audit atomically; T2 is approval
  decision CAS; T3 revalidates task/action/approval and attempt uniqueness before
  creating a Run; T4 binds Run transitions to required evidence; T5 requests
  quiescent Task pause and rechecks the Task state at Run creation/start edges.
  Human approval and later Run creation do not need one transaction.
- Audit is a per-workspace append-only hash chain. Sequence allocation is an
  atomic unsigned 64-bit operation. `record_hash` is SHA-256 over the UTF-8
  RFC8785-JCS projection excluding `record_hash`, with `prev_hash` included.
  Genesis uses sequence 1 and 64 lowercase zero hex characters. Audit stores
  minimal facts and references, never credentials, tokens or full sensitive
  content by default.
- A local writable authority requires an exclusive OS file lock. Losing the
  lock is read-only/fail-closed. Backups are never automatic parallel
  authorities; restore is explicit and offline. Migration ledgers are monotonic,
  checksum-protected and backed up before writes. Schema/checksum mismatch and
  integrity failure fail closed.
- Application timestamps come from an injected runtime clock. Audit ordering is
  sequence-based, not wall-clock-based. CAS mismatch maps to `ExternalConflict`;
  persistence corruption, unavailable authority and migration failures remain
  fail-closed canonical errors.

## Consequences

Repository adapters can be implemented against the contract without changing
core domain semantics. SQLite configuration details such as busy timeouts and
WAL pragmas remain adapter choices within the canonical guarantees. FTS5,
connectors, scheduler services, erasure orchestration and distributed
multi-master resolution are outside this milestone.

## Rejected alternatives

- A constrained SQLite prototype before contract closure would make unratified
  schema and concurrency choices de facto product semantics.
- Coupling Action, Approval and Run creation into one transaction would make a
  human approval lifecycle impossible to represent correctly.
- Rewriting or deleting historical audit records during normal erasure would
  break the chain; privacy minimization and opaque/tombstone references happen
  before append.
