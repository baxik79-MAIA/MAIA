# M0.11 Alpha 1 native desktop verification

M0.11 adds the first runnable native MAIA desktop surface using `eframe` over
the accepted Rust Core, authoritative SQLite adapter and loopback-only local
briefing adapter. It is a presentation adapter, not a new semantic authority.

The Alpha 1 flow accepts one explicitly chosen UTF-8 `.txt` or `.md` file,
creates an immutable MAIA-owned artifact snapshot with a content hash and an
append-only audit record, then builds a bounded M0.10 briefing packet from
those snapshots. It calls only `127.0.0.1:11434` with the qualified local Qwen
model. The returned response must pass the existing citation validation before
it is atomically persisted with its packet, result, provenance and audit event.
The desktop history reloads artifacts and accepted briefings from SQLite after
restart. Citation inspection uses the recorded packet snapshots, and the
surface does not make file paths primary user-facing citations.

This slice exposes no connector, HTTP listener, cloud fallback, Approval,
Decision, Commitment, WorkGraph promotion or execution control. Accepted
briefing results retain `execution_authority=false` structurally and at the
persistence boundary.

From a Windows developer checkout with the documented Rust/MSVC prerequisites,
run `./tools/Start-MAIA-Alpha1.ps1`. The launcher selects only the existing
`maia-desktop` package/bin with `--locked --no-default-features`, resolves the
workspace from the script location, and propagates Cargo's exit code. Cargo may
fetch uncached dependencies. `-Release` chooses Cargo optimization; it does not
qualify DEPLOYMENT_LOCKED, sign or install an artifact.

The launcher does not start/install the model runtime or a service, change
provider/model selection, import an evidence file, or retry a failed launch.
The existing desktop owns its loopback-unavailable diagnostics, explicit file
selection, SQLite configuration and opt-in review/capture behavior.

For launcher-only process checks, run
`./tools/tests/Test-Alpha1Launcher.ps1`. It uses a temporary synthetic checkout
and fake `cargo.cmd`: paths with spaces/foreign working directory, Debug/Release
selection, single invocation, exit23 propagation and refusal of unknown flags
or missing checkout inputs. It does not build or launch MAIA or a model.

The approved dependency record is [M0.11 dependency provenance](M0.11_DEPENDENCY_PROVENANCE.md).


## Read-only Supervisor telemetry (development slice)

The desktop separately projects reported local Supervisor metadata and a fresh
query of the reported process identity. It never submits these facts to a
briefing/provider or changes Supervisor state, queue, prompts, keys or grants.
A matching owned query handle and fresh same-run controller telemetry (not a worker-origin signal) establish only
that the reported PID/birth tuple was observed alive or exited. Missing identity,
stale/missing controller telemetry, PID reuse, query/read failures and expired observations
show Unconfirmed. Prior confirmed observation time stays explicitly historical.
Technical exit0 is insufficient for semantic success; is_error=true remains a
reported failure. The current legacy terminal state lacks a birth tuple and has
a historical heartbeat, so it remains reported history with no live/semantic
success claim. This advances original-plan criterion4 only; it is not FU2/FU3,
Begin, deployment acceptance or full MAIA1.0. The private telemetry contract is
`spec/supervisor_status.yaml`; canonical Task/Action/Run FSMs are unchanged.

The observation TTL is ten seconds from a monotonic timestamp captured before
reading/querying the source. Queue delay, UI delivery and repaint do not renew
that lifetime. A late result becomes historical immediately on receipt. The
Supervisor view has its own five-second refresh cadence, wakes on completed
reads and schedules a repaint at the earlier next-probe or observation-expiry
boundary. Expiry clears current presence and keeps last-confirmed details.


## Explicit data for a built unsigned staging artifact

A prepared artifact places `Start-MAIA-Alpha1-Staging.ps1` at its root and the
built Windows binary at `bin/maia-desktop.exe`. From Windows PowerShell5.1:

```powershell
./Start-MAIA-Alpha1-Staging.ps1 -DataDirectory C:/MAIA/staging/alpha1/profile-a
```

The data directory must be an explicit drive-absolute path. An explicit
`-ArtifactDirectory` must also be drive-absolute and name an existing literal
directory; its default remains the packaged launcher directory. The launcher runs
the packaged EXE directly, requires no Cargo checkout, and sets four file paths
only in that child: `workspace.sqlite3`, `health.sqlite3`, `ui.json` and
`diagnostics.log` below the chosen directory. It clears inherited
`MAIA_CAPTURE_*` and `MAIA_REVIEW_*` development hooks. It propagates the actual
application exit; normal interactive use waits for the user to close the app.
An acceptance runner must independently bound and settle its owned processes.

`MAIA_ALPHA1_DATABASE` and `MAIA_LOCAL_INTELLIGENCE_HEALTH_DB` retain their
existing behavior. The desktop now also accepts `MAIA_ALPHA1_PREFERENCES` and
`MAIA_ALPHA1_DIAGNOSTICS`; when absent, their previous `C:/MAIA` defaults remain.
A present empty/invalid preferences or diagnostics override does not fall back
to another profile. These two writes remain best effort, as before; this is not
a database migration or a persistence guarantee for preferences/diagnostics.

The existing loopback availability probes, explicitly requested local briefing
and read-only installed Supervisor telemetry remain application capabilities.
The launcher does not install/start a model or service, import evidence, invoke
Begin/FU2/FU3, enable evolution, verify signatures, migrate an installed profile
or perform an update. Development capture hooks remain compiled; removing their
inherited environment is not a DEPLOYMENT_LOCKED construction proof.

`./tools/tests/Test-Alpha1StagingLauncher.ps1` compiles one temporary synthetic
EXE and checks six finite cases: spaces/profile paths/child environment and
exit23, missing EXE, unknown option, drive-relative and root-relative data
refusal, and specific relative/drive-relative artifact refusal before data creation.
It retains failed fixtures for diagnosis and never launches the real product.

Before claiming backup or rollback acceptance, use the actual SQLite adapter
contracts and schema evidence. An unsigned new staging folder is not a signed
update under `spec/deployment.yaml`, and these checks do not accept V001–V005 or
full MAIA1.0. The older supported artifact and compatible offline data snapshot
must be established explicitly; never infer schema compatibility from a copied
file or an EXE hash.
